# Project Summary: High-Velocity Flash Sale Ticketing Platform

### Situation
Concert ticket sales and high-demand flash sales regularly experience massive traffic surges (thundering herds) the instant sales go live. Conventional transactional architectures often suffer from severe latency, complete system crashes, and the critical problem of overselling available physical seats due to database race conditions. This damages organizer brand credibility, causes immense buyer frustration, and introduces heavy operational overhead resolving customer disputes and manual refunds.

### Task
The objective was to architect and deliver an end-to-end distributed ticketing platform capable of handling hundreds of requests per second, enforcing strict inventory consistency with a guaranteed 0% overselling rate, eliminating duplicate transactions from rapid-fire clicks, providing an orderly virtual waiting room with real-time queue visibility, integrating multi-method payment flows, and issuing self-service digital e-tickets with tamper-proof audit trails.

### Action
Architected a high-throughput system using Go, GraphQL (gqlgen), and React 18 featuring a defense-in-depth inventory protection strategy. On the first layer, an atomic Lua script in Redis (DecrStockAtomic) performs fast in-memory quota decrements before requests hit the database. The second layer applies conditional relative SQL clauses in PostgreSQL backed by automated compensating rollbacks upon failure. Transaction flows were decoupled into a fast critical path and an asynchronous background worker pool orchestrated through RabbitMQ with Dead-Letter Queues and exponential backoff retries. The solution incorporated a virtual waiting room using Redis Sorted Sets with a live queue radar, 5-minute single-use checkout passes, an Idempotency-Key mutex guard to block duplicate orders, an automated background reconciliation worker with an in-flight grace period and automatic expiration of abandoned reservations, an integrated Midtrans Snap payment simulator, e-ticket generation with barcodes and QR codes, and an administrative command center for turnover monitoring and batch queue admission.

### Result
Stress testing with k6 demonstrated a 0.00% HTTP error rate with throughput up to 138 requests per second under sudden spikes of up to 300 concurrent virtual users. Under high-contention testing where 500 concurrent users executed 2,000 checkout attempts for 100 limited tickets, the platform sold exactly 100 tickets, gracefully rejected the remaining 1,900 requests, and left the database with exactly 0 remaining stock and a verified 0% overselling rate. All automated test suites, including Go race condition detection, mid-transaction broker failure rollbacks, and Playwright browser flows, passed with zero inventory leakage.
